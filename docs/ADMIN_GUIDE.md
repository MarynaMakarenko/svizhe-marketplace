# Посібник адміністратора системи

Для людини, яка підтримує сервер: стежить, щоб сайт працював, робить резервні копії, оновлює.
Про керування продавцями й категоріями на самому сайті — у [посібнику користувача](USER_GUIDE.md#адміністратор-майданчика).

## Що де зберігається

| Дані | Де | Чи потрапляє в резервну копію |
|---|---|---|
| Користувачі, товари, замовлення, відгуки | том Docker `db_data` (PostgreSQL) | так |
| Фото товарів | том Docker `uploads` | так |
| Налаштування і паролі | файл `.env` у каталозі проєкту | **ні — збережіть окремо** |
| Журнали | журнали Docker | ні |

Команда `docker compose down` дані **не** видаляє. Дані видаляє лише `docker compose down -v`.

## Щоденний контроль

```bash
docker compose ps                      # усі три сервіси Up, db і backend — healthy
curl -s http://localhost:8088/api/health   # {"status":"ok"}
```

`/api/health` повертає 200 лише тоді, коли системна частина має зв'язок із базою, тому цю адресу зручно під'єднати до будь-якого зовнішнього монітора доступності.

## Журнали

```bash
docker compose logs backend --tail 100      # останні 100 рядків
docker compose logs backend -f              # стежити в реальному часі
docker compose logs backend | grep ПОМИЛКА  # лише внутрішні помилки
```

Кожен запит до API — один рядок: час, метод, адреса, код відповіді, тривалість:

```
2026-11-14T15:20:41.512Z POST /api/orders 201 38ms
```

Коди `4xx` — помилка користувача (невірний пароль, товару немає на складі), це нормальна робота.
Код `500` і рядок зі словом `ПОМИЛКА` — збій, який варто розібрати: поруч у журналі буде текст помилки.

## Резервне копіювання

```bash
./scripts/backup.sh
```

Створює каталог `backups/svizhe-РРРРММДД-ГГХХСС/` з двома файлами: `db.sql.gz` (база) і `uploads.tar.gz` (фото).
Сайт під час копіювання продовжує працювати.

Зберегти в інше місце: `./scripts/backup.sh /mnt/disk/backups`.

**Автоматично щоночі о 03:00** — додайте рядок у `crontab -e`:

```
0 3 * * * cd /шлях/до/svizhe-marketplace && ./scripts/backup.sh >> backups/backup.log 2>&1
```

Видаляти копії, старші за 30 днів:

```
30 3 * * * find /шлях/до/svizhe-marketplace/backups -maxdepth 1 -name 'svizhe-*' -mtime +30 -exec rm -rf {} +
```

> Копії на тому самому диску не рятують від поломки диска. Регулярно переносьте каталог `backups/` і файл `.env` на інший носій.

## Відновлення

```bash
./scripts/restore.sh backups/svizhe-20261114-030000
```

Скрипт запитає підтвердження, зупинить API, замінить базу й фото даними з копії та запустить API знову. Простій — кілька секунд.
Усе, що з'явилося після створення копії, буде втрачено.

### Перенесення на інший сервер

1. На старому сервері: `./scripts/backup.sh`.
2. Скопіюйте на новий сервер каталог проєкту (або `git clone`), файл `.env` і каталог з копією.
3. На новому сервері: `docker compose up -d --build`, далі `./scripts/restore.sh <каталог копії>`.

## Оновлення

```bash
./scripts/backup.sh                 # копія перед оновленням
git pull
docker compose up -d --build
```

Нові міграції бази застосовуються автоматично під час старту системної частини; уже застосовані повторно не виконуються (облік — у таблиці `schema_migrations`).

Якщо після оновлення щось зламалося: поверніть попередню версію коду (`git checkout <попередній коміт>`), зберіть знову й відновіть копію.

## Типові операції

**Призначити адміністратора**

```bash
docker compose exec db psql -U svizhe -d svizhe -c "UPDATE users SET role = 'admin' WHERE email = 'user@example.com'"
```

**Скинути пароль користувача.** Паролі зберігаються лише як хеші, тому новий хеш потрібно згенерувати:

```bash
docker compose exec backend node -e "import('bcryptjs').then(b => b.default.hash('НовийПароль123', 10).then(console.log))"
docker compose exec db psql -U svizhe -d svizhe -c "UPDATE users SET password_hash = '<хеш з попередньої команди>' WHERE email = 'user@example.com'"
```

**Змінити порт сайту.** У `.env` змініть `WEB_PORT`, потім `docker compose up -d`.

**Відкрити консоль бази**

```bash
docker compose exec db psql -U svizhe -d svizhe
```

**Почати з чистої бази** (усі дані буде видалено):

```bash
docker compose down -v
docker compose up -d --build
```

**Перевірити, що система справна після змін**

```bash
docker compose exec backend npm test
```

Тести працюють в окремій тимчасовій базі й робочих даних не зачіпають.

## Доступ з інтернету та HTTPS

Контейнер `frontend` віддає сайт по HTTP. Для публічного сервера поставте перед ним зворотний проксі з сертифікатом, наприклад [Caddy](https://caddyserver.com/) — він отримує й оновлює сертифікат Let's Encrypt сам. Файл `Caddyfile`:

```
shop.example.com {
    reverse_proxy localhost:8088
}
```

Порт бази назовні не відкривається: до PostgreSQL мають доступ лише контейнери проєкту.

## Несправності

| Симптом | Що перевірити | Рішення |
|---|---|---|
| Сайт не відкривається | `docker compose ps` | Якщо сервіси не `Up` — `docker compose up -d`. Якщо Docker не запущено — запустити його. |
| Сторінка є, але «Немає зв'язку із сервером» | `docker compose logs backend --tail 50` | Найчастіше база ще стартує — зачекайте 10–20 секунд. Якщо в журналі `password authentication failed` — пароль у `.env` не збігається з тим, з яким створено базу: поверніть старий пароль. |
| `backend` у стані `Restarting` | `docker compose logs backend` | Помилка міграції або підключення до бази — текст буде в останніх рядках журналу. |
| Не завантажуються фото товарів | розмір і тип файлу | Дозволені JPG, PNG, WebP до 3 МБ. |
| Закінчилося місце на диску | `docker system df` | `docker image prune -f` видаляє старі образи; перенесіть старі копії з `backups/`. |
| Користувач не може увійти | розділ «Користувачі» в адмін-панелі | Перевірте, чи акаунт не заблоковано; за потреби скиньте пароль (вище). |
| Після перезавантаження сервера сайт не піднявся | `systemctl is-enabled docker` | `sudo systemctl enable docker` — контейнери стартують разом із Docker. |
